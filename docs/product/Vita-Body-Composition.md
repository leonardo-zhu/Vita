# Vita — 身体成分模块（草案 v0.1）

> 用阿福体脂秤（AFU-WL-TZ-A1）测体重与阻抗，在 Vita 里算出并展示完整的身体成分指标、趋势和判定，替代厂商 App「蚂蚁阿福 · 身材管理」。本文是产品与算法草案；协议细节见附录，实现细节落地时再拆进 TDD。
>
> 本文所有官方 App 数据于 2026-11-03 从用户手机（iPhone 镜像）上的「身材管理」页面读取；协议结论来自同日 Vita 真机抓包。

------------------------------------------------------------------------

## 1. 定位

- **目标**：Vita 成为体脂秤的唯一伴侣 App。打开称重页就能完成"同步离线记录 → 称重 → 看到全部指标 → 写入 Apple 健康"，不再需要厂商 App。
- **和 Vita 主线的关系**：身体成分是饮食目标的输入。去脂体重、基础代谢直接决定蛋白质与能量目标；长期趋势（脂肪量降、肌肉量稳）是减脂增肌是否有效的判据，也是 Agent 给建议的依据。
- **诚实原则**：秤真正测到的只有**体重**和**下肢阻抗**两个物理量，其余全是估算。界面上区分"测量"与"估算"，估算项不装作精确。

## 3. 对标：官方「身材管理」页面

### 3.1 页面结构

1. **顶部**：设备连接状态（"连接中，请轻踩体脂秤唤醒设备"）、kg / 斤切换、成员切换（多用户）。
2. **最近一次**：日期翻页、体重大字、较上次变化、BMI、体脂率、"N 项异常"与「测量详情」。
3. **测量详情**（弹层）：按次列出全部测量，每次展开 19 项指标，每项有判定标签（偏低/标准/偏高/过高/优秀），再展开是区间刻度条和一句解释。
4. **核心指标**趋势：体重 / BMI / 体脂率 / 腰围，时间范围可选。
5. **脂肪管理**趋势：脂肪量 / 内脏脂肪等级 / 皮下脂肪量 / 皮下脂肪率。
6. **肌肉状态**趋势：肌肉量 / 肌肉率 / 骨骼肌量 / 骨骼肌率。
7. **全部数据来源**、「去记录」（手动记录）、「AI 智能解读」、打卡。

## 4. 指标与算法

### 4.1 三层结构

```text
测量（秤）        体重、阻抗 a/b
   ↓
核心估算（模型）  体脂率 ← 体重、阻抗、身高、年龄、性别
   ↓
推导（换算）      脂肪量、去脂体重、肌肉量、基础代谢……
```

核心估算一旦准确，推导层就跟着准。所以**先把体脂率做对**，其余指标才有意义。

### 4.2 体脂率（核心，需校准）

- **现状**：`1.2 × BMI + 0.23 × 年龄 − 10.8 × 男 − 5.4 + 1.5`（Deurenberg，沿用 AFUScale）。只用身高体重，阻抗仅用来判断是否光脚。同体重不同阻抗时，秤上数字会变，Vita 的不变。
- **官方算法拿不到**：反编译 APK，`ICAlgorithmManager.calc` 是空实现（原样返回输入），Java 层没有任何体脂公式或系数；DEX 里有 `bodyfat_source` 字段名，体脂率可能来自服务器或其他地方。秤自己的 MCU 也在算（离线时屏幕上有体脂率），但不经蓝牙回传。
- **方案：用你自己的数据拟合**。BIA 秤的通用形式：

  ```text
  体脂率 = a · 身高² / 阻抗 + b · 体重 + c · 年龄 + d   （单一用户、性别固定）
  ```

  1. 称重页显示每次的阻抗 a/b，用户记下同一次秤屏幕上的体脂率；
  2. 收集 ≥ 6 组，体重有一定跨度（早晚各称一次）；
  3. 最小二乘拟合 a、b、d（年龄短期不变，c 并进常数），留一组做验证，误差目标 ±0.5 %；
  4. 系数写成带版本号的配置；未校准时继续用 BMI 公式，并标注"估算"。
- 阻抗用哪一路（a 或 b，或两者组合）也由拟合决定。现有样本：实时锁定帧 512/452 Ω，离线记录 552/486、539/475 Ω。

### 4.3 推导指标（用样本验算过的换算关系）

| 指标 | 公式 | 样本验算 |
| --- | --- | --- |
| 脂肪量 | 体重 × 体脂率 | A：76.8 × 21.4 % = 16.4 ✓ |
| 去脂体重 | 体重 − 脂肪量 | A：60.4 ✓；B：60.25 ≈ 60.20 ✓ |
| 肌肉量 | 去脂体重 − 骨量 | A：60.4 − 3.3 = 57.1 ✓；B：56.9 ✓ |
| 肌肉率 | 肌肉量 ÷ 体重 | A：74.3 % ✓ |
| 体水分量 | 体水分率 × 体重 | A：44.8 ✓；B：44.1 ✓ |
| 骨量占比、骨骼肌率、皮下脂肪率、蛋白质占比 | 对应质量 ÷ 体重 | 均 ✓ |
| 基础代谢 | 370 + 21.6 × 去脂体重（Katch-McArdle） | A：1674 ✓；B：1671 ✓ |

### 4.4 经验估算（公式未知，需要另行确定）

| 指标 | 从样本看出的线索 | 处理 |
| --- | --- | --- |
| 体水分率 | ÷ 去脂率：A 0.741，B 0.733，不是常数，应与阻抗有关 | 与体脂率一起拟合，或取公开 BIA 公式 |
| 骨量 | 两次都 3.3 kg，不随小幅体重变化 | 公开经验公式（按去脂体重分段） |
| 骨骼肌量 | ÷ 肌肉量：A 0.578，B 0.569 | 公开公式（Janssen 等）或拟合 |
| 皮下脂肪量 | ÷ 脂肪量：A 0.720，B 0.715 | 暂按约 0.72 × 脂肪量 |
| 蛋白质 | 不等于"肌肉量 − 体水分"（A 差 0.7 kg） | 公开公式，标注估算 |
| 内脏脂肪等级 | 两次都 7.0 | 公开经验公式（BMI、年龄、腰围），标注估算 |

这一层先做"能显示、明确标注估算"，校准优先级低于体脂率。

### 4.5 不做的

- 身体年龄、身体评分：没有医学定义，各厂商算法不同（通常拿体脂率、基础代谢和同龄均值比），无法验证，不做。官方「身材管理」里也没有这两项。
- 体型判断（M4 可选）：BMI × 体脂率的九宫格分类，例如"隐形肥胖"（BMI 正常、体脂高）、"肌肉型"（BMI 高、体脂正常）。不带来新信息，但便于理解，成本很低。
- 腰围：秤测不到，作为手动记录项预留（官方"核心指标"里有）。

## 5. 数据与存储

**原则：存原始测量，指标读时计算。**

- Vita 本地存每次称重的原始记录：时间、体重、阻抗 a/b、来源（实时 / 离线同步）、时间是否可靠、当时的身高年龄性别快照。
- 所有估算指标由「算法版本 + 原始记录」即时算出。校准系数更新后，历史趋势整体重算，不会出现新旧算法混在一张图里。
- 这一模块的原始称重**由 Vita 拥有**（秤确认后就删了，厂商 App 也拿不到），与 PRD §7.1 "体重由外部平台拥有"不同，需要同步修改 PRD 的数据所有权表。

**写入 Apple 健康**：

| HealthKit 类型 | 写入 |
| --- | --- |
| Body Mass | 是（已实现） |
| Body Fat Percentage | 是（已实现；校准后改用新算法） |
| Lean Body Mass（去脂体重） | 是（新增） |
| Body Mass Index | 可选，健康 App 能自己算，倾向不写 |
| 其余指标 | 健康里没有对应类型，只存 Vita |

基础代谢不写：HealthKit 的 Basal Energy Burned 是按时间累加的能量，含义不同，写进去会和手表的数据重复。

## 6. 界面

在 Data 页健康卡片里，现有「体脂秤」入口升级为**身体成分**页（独立导航页，不再是弹层）：

1. **称重区**：连接状态、实时体重；打开即同步离线记录，结果并入历史。
2. **最近一次**：体重、体脂率、BMI、较上次变化；N 项异常。
3. **指标列表**：按"测量 / 估算"分组，每项带判定标签、区间刻度条、一句解释；估算项角标"估算"。
4. **趋势**：核心（体重、体脂率、去脂体重）/ 脂肪 / 肌肉三组，周 / 月 / 全部。图表遵循现有 Vita 视觉风格。
5. **历史记录**：按天列出每次称重，可删除单条（同时删除健康里的对应 Sample）。
6. **校准**：显示阻抗，录入秤屏幕上的体脂率，显示已收集组数与拟合误差。

## 7. 与 Vita 其他部分的联动

- **目标生成**：目标计算优先用最近一次称重的去脂体重（蛋白质按去脂体重给，比按体重更合理），需要在 GoalRecommendationPolicy 里评估。
- **Agent 工具**：新增读取身体成分与趋势的工具（"这两周肌肉掉了吗"）；Agent 只读，不改称重记录。
- **HealthKit 同步映射**：称重写入健康时记录 Sample UUID，删除或重算时同步删除旧 Sample，沿用膳食的 HealthKit Sync Mapping 设计。今天这次全量删除健康数据，就是缺了这一步的代价。

## 9. 开放问题

- 体脂率拟合用哪一路阻抗、需要几组才稳定，要看数据。
- 秤屏幕上的数字和官方 App 是否一致？（官方 App 的体脂率可能来自服务器）以秤屏幕为准还是以官方 App 为准，需要先比对一次。

## 附录 A：协议要点（已真机核对）

服务 `FFB0`，写 `FFB1`，通知 `FFB2`。所有帧 20 字节，`AC 29` 开头，字节 18 是帧类别，字节 19 是字节 2–18 的累加和。

| 帧 | 字节 18 | 内容 |
| --- | --- | --- |
| 实时体重 | `D5` | 字节 2 最高位 = 稳定；体重在 3–5 |
| 锁定结果 | `D6` | 字节 2 = `02`；阻抗 a 在 4–5，b 在 6–7；体重在 10–12 |
| 离线记录 | `D8` | 时间在 3–6（大端秒数）；体重在 8–10；阻抗 a 在 11–12，b 在 13–14 |
| 控制 / 签名 | `DF` | 字节 2 是操作类型 |

- **体重编码**：三字节 `hi mid lo`，克数 = (hi − 0x68) × 65536 + (mid << 8 | lo)。AFUScale 网页版"取低 18 位"的解法是错的。
- **握手**：对时（`DF 08`）→ 用户列表（`D4`）→ 当前用户（`D7`）→ 签名（`DF 06`，秤回 5 帧，每帧回 `DF 07`）→ 唤醒（`DF 03`）。实测秤收到对时后就开始发离线记录，签名不是前提。
- **离线记录**：不回确认，秤每约 1.5 秒重发同一条；回 `AC 29 04 D8 … DF BB` 后，秤删除这条并立即发下一条。按旧到新顺序发送。
- **时钟**：秤按**大端**读对时帧里的时间，离线记录的字节 3–6 就是大端 Unix 秒。已真机核对：按大端对时后，17:02 离线称重的记录为 `6A E9 A3 3D`（17:02:37）。网页版按小端写，秤的时钟就成了字节颠倒的值，旧记录因此解出 2065、2073 年。例外：有一条记录 `88 97 F2 41` 解不出合理时间，出现在一次握手中途断开之后，原因未明；解出来晚于现在的一律按同步时间保存。
- **握手中途不要确认离线记录**：真机上在握手指令之间回了 `DF 04 D8`，秤随即断开、换了蓝牙地址重新广播，重连后不再发任何数据。现在等握手指令发完才处理离线记录。
- **不可信的字段**：网页版说 D8 的 11–15 是"模式 / 条数 / 阻抗"，与实测不符。
