# Vita — 产品需求文档 (PRD v0.6)

> **2.0 说明：** 本文是 1.0 的产品基线，仍然有效的规则在 2.0 继续沿用；“数据只在本机”相关的部分已被《Vita PRD v2.0》取代。

> 个人自用 AI 健康助理 App。核心是一个能对话的 Agent，帮助记录饮食、追踪营养摄入、结合健康数据给出目标与建议。饮食记录与数据看板是当前主要落地形态，但产品定位是"专业 AI 健康助理"，能力边界会持续扩展，不局限于记录本身。

**v0.6 相对 v0.5 的主要变化**：

- 移除"跨天编辑"概念，改为**按日期切换 Session 编辑**：Session 绑定日期，在哪个日期的上下文中，就操作哪一天的 Record。
- Session 组织重新定位：用户回顾时默认看 Data，对话记录折叠；侧边栏按日期列表组织，不展示"会话标题"。
- Pending 明确时效规则：超时自动取消、跨天自动取消，不落库。
- 目标修改明确不走 PendingAction，采用"明确指令直接执行 / 模糊建议对话内确认 / 首次生成一次性确认"。
- 新增 Onboarding 章节，含 HealthKit 数据缺失兜底。
- 移除 PRD 中的数据结构字段表与枚举定义，相关内容迁移至《Vita 技术设计文档（TDD）》，PRD 只保留产品概念与规则。
- Audit Log 口径调整：Agent 操作日志保留（技术侧），面向用户的修改历史 / 回滚 UI 暂缓。
- 明确公共营养参考库为静态只读，不需要版本化。

## 1. 产品定位

- **不是**一个纯粹的饮食记账 App，而是一个**具备工具调用能力、能读取身体数据、能对话交互的 AI 健康助理**。
- 记录摄入、计算营养摄入是当前 MVP 的主要使用场景，但 Agent 的能力边界应设计为可扩展的——后续可以持续增加新的"工具"（tools），让它承担更多分析/建议类的职责。
- 产品交互上采用**统一 Vita Agent 入口**，不按"饮食 Agent / 营养库 Agent / 健康 Agent"等拆成多个独立聊天。
- 个人自用，不上架 App Store，不考虑多用户场景。

## 2. 背景与目标用户

- 用户本人处于减脂增肌周期，需要每天关注蛋白质、热量等关键营养指标是否达标。
- 拥有厨房电子秤，可以较精确地称量食材/食物重量。
- 日常摄入的食品种类相对稳定，适合维护一个小规模、个人化的 Nutrition DB。
- 技术背景为软件工程 / CS 出身，全栈开发经验为主，同时具备原生 iOS（Swift）开发能力——具体客户端技术栈选型见《Vita 技术设计文档》，不在 PRD 中展开。

> 技术选型、架构、数据结构与实现细节见独立文档《Vita 技术设计文档（TDD）》，本文档聚焦产品功能、交互设计与核心业务规则。

## 3. 核心模块

### 3.1 对话式记录（Meal Logging Agent）

**用户故事**：用户吃完一次摄入后，直接用自然语言告诉 Agent 吃了什么（品类、具体食品、做法、称重克数、包装单位等），Agent 完成营养计算并生成待确认的记录卡片。

**核心概念**：

- **Agent Session 按天组织**：Vita 一个 Session 对应一天。Session 的日期同时也是 Agent 操作 Record 的**上下文日期**——在哪个 Session 中，就操作哪一天的 Record。
- **Consumption Record**：一条 Record 代表一次独立的"摄入事件"，而不是固定的早餐/午餐/晚餐实体。
- **Consumption Item**：Item 是营养计算的最小单位。一次 Record 可以包含一个或多个 Item。
- **Group**：Group 是可选的菜品/组织名称，例如"番茄炒蛋"。Group 不是 Food，不拥有独立 Nutrition，只用于把多个 Item 组织在一起。
- **Meal Label**：早餐/午餐/晚餐/零食只是可选语义标签，不是 Record 成立的必要条件。

**流程**：

1. 用户在某个日期的 Session 中输入（文本对话）描述一次摄入内容，例如："中午吃了 200g 鸡胸肉，150g 米饭，一点生抽。"
2. Agent 判断用户是在创建新的 Consumption Record，还是在追加/修改已有 Record：
   - 如果语义上明显是在补充刚才或某次已存在摄入，例如"对了，还有一杯牛奶"，则追加到对应 Record；
   - 如果用户明确表达为另一时间点或另一摄入事件，例如"下午三点又喝了一杯牛奶"，则创建新的 Record；
   - 时间间隔只能作为辅助信号，不设置机械时间窗口。
3. Agent 结合当前营养数据来源做匹配判断，按以下优先级查找（详见 3.2）：
   1. 用户 Nutrition DB 中的 Food Product / Food Version（品牌/个人具体产品）；
   2. 公共营养参考库中的通用食材条目；
   3. 均无匹配或食品本身没有营养成分表依据时，由 Agent 对该 Consumption Item 做 AI Estimate，不写入任何数据库。
4. Agent 生成一张**待确认卡片**，展示：
   - 本次 Consumption Record 的 event_time、可选 meal_label；
   - 识别出的每项 Item；
   - 每项的用量、用量来源、营养数据来源；
   - 每项及汇总的蛋白质、脂肪、碳水、热量；
   - 如有 Group，则展示 Group 名称及其包含的 Items。
5. 用户在卡片上点击【记录】才真正落库；点击忽略/不处理则不落库、不写入任何数据库。
6. Agent **不会**在未经用户确认的情况下自动写入正式的饮食记录，也不会自动把估算值沉淀进用户 Nutrition DB。

**Consumption Record 时间规则**：

- `event_time` 表示实际摄入时间。
- `created_at` 表示用户什么时候在 Vita 中录入。
- 两者必须分离，不能用录入时间替代实际摄入时间。
- 当用户只提供"今天中午""晚上"这类模糊时间时，Agent 不应伪造精确时间，应保留时间精度信息（例如精确时刻 / 大致时刻 / 时段 / 仅日期）。
- 时间精度的具体标记方式与存储格式见 TDD。

**Consumption Record 可后续修改**：

- Record 创建后不是封闭日志，后续仍可通过对话被 Agent 定位、追加、修改或删除 Item。
- 示例：
  - "中午其实还喝了一杯牛奶" → 追加到中午那条 Record；
  - "中午鸡胸肉不是 200g，是 180g" → 修改已有 Item 用量；
  - "中午其实没吃鸡蛋" → 删除或取消对应 Item。
- 修改后重新计算该 Record 与当天汇总数据。
- MVP 不保留面向用户的修改历史 / 回滚 UI（Agent 操作日志另见 TDD）。

**Session 与日期规则**：

- 一个 Session 对应一天，Session 日期即 Agent 操作 Record 的上下文日期。
- 打开 App 默认进入当天 Session。
- 侧边栏按日期组织 Session 列表，不展示"会话标题"。
- 用户回顾某一天时，默认展示该日期的**饮食数据摘要**（Records、Items、营养汇总、目标完成度）；对话记录默认折叠，需要时展开或用于继续修改。
- 跨午夜时自动切换到新一天的 Session，旧对话留在原日期，不产生归属歧义。
- 历史日期的 Session 可继续对话和写入，无特殊规则——切到哪天，就写哪天。
- 如果用户在当前 Session 中提到其他日期（例如"昨天还吃了提拉米苏"），Agent 只提示"这是昨天的内容，要切到昨天记录吗"，不自动跳转，不跨 Session 写入。用户确认切换后再进入对应日期。
- Dashboard 的日历视图 / 侧边栏是切换到对应日期 Session 的入口。

**整条 Consumption Record 删除**：

- 除了 Item 级别的追加/修改/删除，用户也可以要求整条撤销一次 Record（例如"刚才记错了，中午那条删了重新说"）。
- 确认方式与创建/修改一致：需要用户在对话或卡片上明确确认。
- MVP 不保留面向用户的修改历史 / 回滚 UI，删除为硬删除、不可找回。
- 若该 Record 此前已同步写入 Apple Health，删除时需联动撤销对应的 HealthKit 写入，具体机制见 3.3「HealthKit 写入的修改与删除同步」。

**Consumption Item 用量规则**：

- 用户可以用自然语言表达各种单位，例如 g、ml、个、颗、根、片、杯、勺、一盒、半盒、一瓶等。
- 内部营养计算统一标准化到 `g` / `ml`。
- 原始表达应保留，用于回看和解释；计算以标准化后的重量/体积为准。
- 实际称重数据优先于 AI 估算。

示例：

| 用户表达 | 内部处理 |
| --- | --- |
| 200g 鸡胸肉 | 200g |
| 2 个鸡蛋 | 2 个 → AI 估算重量 → 标准化为 g |
| 2 个鸡蛋，称出来一共 108g | 108g，优先使用实测重量 |
| 4 个番茄，一共 612g | 612g，优先使用实测总重量 |
| 半盒牛奶 | 根据 Food Product 的 package_size 转换为 ml |
| 一点油 | AI 粗略估算用量 |

**Amount Source 与 Nutrition Source**：

- 摄入量来源（amount source）与营养数据来源（nutrition source）是两个独立概念，展示时需区分。
- 例如"两个鸡蛋，称出来 108g"：用量来源是用户实测，营养来源是 AI 估算。
- 例如"半盒已录入包装牛奶"：用量来源是包装换算，营养来源是用户 Nutrition DB。
- 例如"200g 鸡胸肉"命中公共营养参考库：用量来源是用户实测，营养来源是公共参考库。
- 具体枚举值与存储方式见 TDD。

**Agent 询问规则**：

- Agent 应最大化利用已有数据减少用户重复输入，但不得在存在实质性歧义时擅自制造事实。
- 如果 Nutrition DB 中只有一个明确匹配的"嫩豆腐"，用户说"吃了 200g 嫩豆腐"，可以直接使用。
- 如果 Nutrition DB 或公共参考库中有多个可能匹配项，Agent 必须询问用户选择。
- 如果用户说"半盒牛奶"，且对应 Food Product 已有 package_size，可以直接换算。
- 如果用户说"一个番茄"，但没有重量信息，Agent 可以估算并标记为 AI estimated；如果用户在同一上下文中表示可以称重，则应优先询问或等待实测重量。
- 如果熟重/生重不明确，且会显著影响计算结果，Agent 必须询问。例如"200g 鸡胸肉"在熟重与生重营养换算差异明显时，不应擅自假设（公共参考库中生/熟通常是不同条目，命中多个候选时同样适用"多候选必须询问"规则）。
- 不能从历史记录擅自复制本次用量。只有用户明确表示"和中午一样"等语义时，才可复用历史 Record / Item 的结构或用量。

**调味料与小量成分处理**：

- 油、糖、酱油等可能对热量或钠等指标有实际影响的成分，Agent 可以作为 Item 粗略估算并纳入营养计算。
- 盐、葱花、黑胡椒等营养影响极小的成分，可以记录为 Item 但不纳入营养汇总，或在不影响记录理解时直接忽略。
- Item 可具有"是否纳入营养汇总"的概念，用于决定该 Item 是否参与汇总。
- 该标记是内部 Agent / Calculation 层面的状态，不作为用户主要交互，不设计成需要用户频繁手动勾选的字段。

**设计要点**：

- 用户 Nutrition DB 的匹配交由大模型自身的语义理解完成，**不额外开发一套独立的字符串模糊匹配/检索算法**——考虑到库的体量很小（预计几十条量级），MVP 阶段直接将整个用户 Nutrition DB 结构化注入 Agent 上下文即可。公共营养参考库体量更大，查询方式不同，见 3.2。
- 是否将某个食品沉淀为用户 Nutrition DB 的正式条目，是用户的**显式确认动作**，与"记录这一次摄入"是两个独立的操作，不能混为一谈。
- 无营养成分表且完全依赖 AI 估算的食品，不进入用户 Nutrition DB，只在具体 Consumption Item 中作为 AI Estimate 使用。

### 3.2 营养数据来源（Nutrition DB + 公共营养参考库）

Vita 的营养数据匹配采用三级优先级：

1. **用户 Nutrition DB**（品牌/个人具体产品，用户显式维护，最高优先级）；
2. **公共营养参考库**（通用食材，标准参考值，见下）；
3. **AI 纯估算**（前两者均无匹配时的最后手段）。

#### 3.2.1 用户 Nutrition DB

**定位**：只收录用户自己实际会吃/喝，并且有可靠营养数据依据的具体食物和饮品。不追求覆盖度，纯手动录入，按需添加。

用户 Nutrition DB 不是公共食品数据库，也不是所有 AI 估算食品的沉淀池。它更接近用户个人的可靠食品资料库。

**录入时机**（不限定固定流程，以下场景均可触发）：

- 新买了某个食品/饮品时随手录入；
- 做完一道菜之后回头补录其中有明确营养标签的食品；
- 对话记录某次摄入时，发现某个有营养成分表的食物库里没有，临时录入；
- 上传或拍摄包装营养成分表图片，由 Agent 解析并生成待确认的 Food Product / Food Version。

**Food Product 定义**：

- Food Product 指具体食品产品，而不是抽象类别。
- "鸡胸肉""牛奶""豆腐"这类更接近食品类别；"某品牌鸡胸肉""某品牌 250ml 纯牛奶""某供应商嫩豆腐"才是更适合进入用户 Nutrition DB 的 Food Product。
- 不同品牌、不同供应商、营养成分不同的产品，可以分别作为不同 Food Product。
- 便利功能（可选，非本版本重点）：允许用户以公共营养参考库的某条数据为起点，新建一个用户自己的 Food Product（例如常吃的某品牌鸡胸肉实际营养跟参考库数值有出入，想按自己校准过的数值维护）。

**Food Product 产品层约定**：

- 包含名称、品牌/供应商（可选）、package_size（可选）、当前 Food Version、备注等。
- package_size 用于理解"一盒、半盒、一瓶、半瓶"等输入。
- 具体字段定义与存储方式见 TDD。

**Food Version 产品层约定**：

- 同一 Food Product 下可有多个 Version。
- Version 不可变：不修改历史 Version。
- 历史 Consumption Item 引用当时使用的 Food Product + Food Version，因此后续用户 Nutrition DB 的变化不会影响历史记录。
- 具体字段（单位基准、蛋白质/脂肪/碳水/热量、原始营养标签图片、数据来源、生效状态、备注等）见 TDD。

**Version 规则**：

- 如果同一个具体食品只是营养标签、包装、供应信息发生变化，应在同一个 Food Product 下创建新的 Food Version。
- 不修改历史 Food Version。
- 如果产品身份本身已经变化，例如"伊利纯牛奶"变成"伊利高钙纯牛奶"，应创建新的 Food Product，而不是只创建 Version。

**package_size 规则**：

- package_size 是 Food Product 的可选辅助属性，不是独立 Entity。
- 它主要用于把"一盒、半盒、一瓶、半瓶"等用户表达转换为 g / ml。
- 例如：Food Product 为某品牌纯牛奶，package_size 为 250ml，用户输入"喝了半盒" → 标准化为 125ml。

**不进入用户 Nutrition DB 的情况**：

- 没有营养成分表，且完全依赖 AI 估算的食品，不进入用户 Nutrition DB。
- 常见的无品牌大宗食材（鸡蛋、番茄、香蕉等）改由公共营养参考库覆盖，见 3.2.2。
- 真正无法归类、无参考依据的食品（复杂菜品、无法归类的外卖菜等）仍然可以被记录到 Consumption Record 中，但营养数据来源标记为 AI estimated。

#### 3.2.2 公共营养参考库

**背景**：鸡蛋、番茄、香蕉、大米这类无品牌大宗食材，此前完全依赖 AI 现场估算，导致同一种食材在不同时间被问到时，估算出的营养数值可能不一致，影响历史数据的可比性。

**定位**：收录不区分品牌的通用食材标准营养成分数据，作为用户 Nutrition DB 之外的第二数据源，保证同一食材长期取值一致，且比 AI 纯估算更可信。

**数据来源**：候选为《中国食物成分表》（覆盖国内日常饮食场景）和/或 USDA FoodData Central（国际食材补充）。具体选型、版本与收录范围留待技术设计文档确定。

**数据形式**：静态数据集（例如 JSON），随 App 内置或首次启动时加载，不依赖网络请求。数据来源与私有使用边界见《公共营养参考库规范》。

**数据性质**：

- 公共营养参考库是**静态只读**数据，不设计版本机制。
- 通用食材的标准营养值不会频繁变化，历史 Consumption Item 引用它即可，不需要额外的一致性机制。
- 如果发现录入错误，可在数据集层面修正；个人自用场景不需要为此设计版本化。

**数据规模**：预计几百至一两千条常见食材，量级远大于用户 Nutrition DB（几十条），因此**不能**像用户 Nutrition DB 一样整体注入 Agent 上下文。

**查询机制**：

- Agent 通过一个「查询公共参考库」工具按食物名称查找，采用精确匹配 + 简单别名表即可，**不需要**构建复杂的语义检索/模糊匹配算法。
- 如果一次查询有多个候选（例如"鸡胸肉"在库中有"生""熟"两种记录），沿用现有的"多候选必须询问用户"规则，不擅自选择。

**与用户 Nutrition DB 的关系**：

- 公共参考库条目**不算作**用户 Nutrition DB 的一部分，两者数据来源标签不同。
- Consumption Item 命中公共参考库时，营养数据来源与用户自建的 Nutrition DB 和纯估算区分标记。

**已知限制**：仍有一小部分食物（复杂菜品、无法归类的外卖菜、自制无参考的料理）三级来源都无法匹配，只能走纯 AI 估算，这部分的数值一致性问题不做处理——出现频率低、影响有限，视为可接受的已知限制。

### 3.3 健康数据集成（Apple Health / HealthKit）

**定位**：Apple Health 是 Vita 当前统一的外部健康数据读取入口，同时也是 Vita 营养数据对外同步的出口。Vita 不负责重新记录用户的睡眠、运动、体重等健康数据，而是读取 Apple Health 中已经汇聚的数据，与 Vita 自己的饮食数据结合分析。

**数据所有权**：

- Vita 自己拥有并维护：
  - 用户 Nutrition DB 与公共营养参考库；
  - Consumption Records / Items；
  - 营养计算结果；
  - User Goals。
- 外部健康平台负责维护身体与活动数据，例如体重、体脂、睡眠、运动、活动能量等。
- Apple Health 中读取到的身体/活动数据不是 Vita 自己的主数据，Vita 只在获得授权后读取所需数据。

**读取的数据类型（初步范围）**：

- 身高（Height）
- 体重（Body Mass）
- 体脂率（Body Fat Percentage）——该字段在 HealthKit 中存在标准类型，但数据来源依赖第三方设备（体脂秤等）同步，需注意用户设备上是否实际存在。
- 出生日期（Date of Birth）
- 生理性别（Biological Sex）
- 睡眠数据（Sleep Analysis）
- 活动/消耗能量（Active Energy）
- 后续根据实际分析需求增加其他健康数据类型。

**用途**：

- 作为每日能量消耗（Energy Expenditure）的数据来源；
- 与 Vita 记录的 Energy Intake 结合，计算 Energy Balance；
- 作为每日目标完成度判断的输入；
- 作为后续健康分析和 AI 建议的基础数据。

**Vita → Apple Health（写入）**：

- Vita 可以将用户已经确认的营养摄入数据写入 Apple Health，例如 Dietary Energy、Protein、Fat、Carbohydrates 等 HealthKit 支持的 Nutrition 数据。
- 写入目的：为未来与 Google Health、Apple Health 等生态做**双向联动与数据备份**——蛋白质等关键营养数据写入 Apple Health 后，可以被其他消费 Apple Health 数据的 App/服务读取和确认。
- 只有已经由用户确认并正式落库的数据才允许同步写入 Apple Health。
- 写入 Apple Health 的数据是 Vita 数据的外部同步结果，不替代 Vita 自己的 Consumption Record 与 Nutrition DB。
- 体脂秤例外：Vita 可以通过蓝牙连接阿福体脂秤（AFU-WL-TZ-A1），把称重锁定后的体重与体脂率写入 Apple Health（Body Mass、Body Fat Percentage）。这两项仍以 Apple Health 为主数据，Vita 只是代替厂商 App 写入；写入权限与膳食写入在同一次授权里申请（授权状态分开判断）；连接健康时还没申请过的，进入身体成分页时补问。没有写入权限或设备不支持时，结果存为手动补录，只用于生成目标。体脂率暂按 BMI、年龄、性别估算（与秤上显示不一致，校准方案见《Vita 身体成分模块》[Vita-Body-Composition.md](Vita-Body-Composition.md)），没测到阻抗时不写体脂率。打开称重页时同步秤里的离线记录。

**HealthKit 写入的修改与删除同步**：

- HealthKit 中的营养数据是**离散的 Sample**——每次写入对应一条独立记录，Apple Health App 展示的"每日总量"是对当天所有 Sample 的聚合，而不是一个可以直接覆盖的单一数值。因此 Record 被修改或删除后，**不能**简单"重新写入"了事：如果不精确删除旧 Sample，重新写入只会新增一条 Sample，导致当日汇总被重复计算。
- 为此引入 **HealthKit Sync Mapping**：Vita 内部维护 Consumption Record（或其营养字段）与对应写入 Apple Health 的 HKSample UUID 之间的映射关系。
- 同步流程：
  1. 用户确认一条 Record 后，若包含需要同步的营养字段，Vita 调用 HealthKit 写入 API 生成对应 Sample，并保存返回的 Sample UUID 到该 Record 的映射记录中；
  2. Record 被**修改**时，Vita 先通过映射找到旧 Sample 并删除，再写入修改后的新值，更新映射；
  3. Record 被**整条删除**时，Vita 通过映射找到旧 Sample 并删除，同时清除该映射记录。
- 边界情况：若用户在 HealthKit 写入权限被撤销期间修改/删除 Record，Vita 应识别当前没有写入权限，仅更新本地数据、不尝试同步，并给出清晰提示（沿用"权限撤销需清晰提示"原则），避免静默产生孤儿数据。

**数据源关系**：

- Vita MVP 不直接读取 Google Health / Google Health API。
- 用户使用的 Fitbit 等设备产生的数据，可以先通过其现有生态进入 Google Health，再由 Google Health / 其他同步机制进入 Apple Health；Vita 不需要在 MVP 中重复实现这一条数据链路。
- Vita 业务层只依赖统一的 Apple Health 数据，不直接依赖具体的上游设备或服务。

**权限处理**：

- Vita 需要分别申请读取和写入所需 HealthKit 数据类型的权限。
- 用户拒绝或撤销权限时，应有清晰提示，避免相关功能静默失效或崩溃。

### 3.4 目标设定（Goal Setting）

**流程**：

1. 首次使用（或用户主动触发）时，Agent 调用工具读取用户的身体数据（身高、体重、体脂率、出生日期、生理性别等，来自 HealthKit）；
2. 结合减脂/增肌目标，由 Agent 自动生成初始的每日目标值（蛋白质、热量等）；
3. 用户可以直接通过对话指令要求 Agent 修改某项目标（例如："把蛋白质目标改成 180g"），Agent 调用对应的"修改目标"工具完成更新。

**能量目标随活动每天变化**（2026-11-02 补充）：

- 用户选择目标类型：维持、减脂（默认少吃约 15%）、增肌（默认多吃约 10%）；调整幅度可以按比例或按千卡设定，界面以“每天缺口 / 盈余多少千卡”显示。
- 每天的能量目标 = 当天预估总消耗（基础代谢 + 活动）按上面的调整。活动随一天变化：早上按平时的活动量估计，白天按 Apple 健康里实际已消耗的不断修正；比平时多出来的运动只计入一半（手表常高估运动消耗）。过去的日子按当天全天实际。
- Data 页同时显示截至当前的热量缺口（已消耗 − 已摄入），与“还可以吃”分开。
- 能量目标不低于基础代谢。用户明确给出能量数值（如“热量目标改成 2000”）时改为固定目标，说“改回自动”恢复。具体公式见 TDD §6.2。

**目标修改的确认规则**：

- 目标修改**不走 PendingAction**，不引入持久化待确认状态。
- 用户明确指令（如"把蛋白质目标改成 180g"）视为确认，Agent 直接执行并复述结果（含旧值与新值）；想反悔时用一条明确指令改回即可，不设专门的撤销功能。
- 用户模糊建议（如"蛋白质目标是不是可以高一点"）由 Agent 给出建议，经**对话内确认**后执行。
- 首次生成目标经**一次性确认**后写入，不进入 PendingAction 队列。

**HealthKit 数据缺失兜底**：

- 若 HealthKit 中关键身体数据缺失，允许用户手动输入或使用估算值生成初始目标。
- 体重是硬门槛：缺失时必须手动补充，否则跳过本次目标生成。
- 体脂率缺失时，用户可手动输入，或选择由 Agent 估算。
- 活动能量缺失时，使用 BMR × 轻度活动系数估算每日总消耗，标记为估算值。轻度活动系数的具体取值见 TDD。
- 出生日期、生理性别若缺失，在 Onboarding 中一次性询问；这些数据用于 BMR 计算。
- 手动输入的身体数据**仅用于目标生成**，不写回 HealthKit。
- 后续 HealthKit 有了数据后，只提示用户"可以重新生成目标"，不自动调整。

**范围说明**：

- 本版本涉及**初始目标的自动生成**、**能量目标随当天活动计算**与**基于用户指令的手动修改**，不包含目标随时间推移的动态自适应调整（例如根据近期体重变化趋势自动调整目标）——该能力留待后续版本，视实际使用数据积累情况再评估是否需要。

### 3.5 数据看板（Dashboard / Data）

**定位**：综合展示饮食记录、营养数据来源与健康数据，支撑用户对减脂进度的整体判断。

Vita 中 Chat 和 Data 是两个不同层：

- **Chat**：用于和 Agent 对话、操作数据、理解数据。
- **Data**：用于查看已经沉淀的数据。用户回顾某一天时，默认进入 Data 视图。

**Data 面板初步信息架构**：

- **Nutrition**：查看用户 Nutrition DB 中的 Food Product / Food Version，以及公共营养参考库的收录情况。
- **Records**：查看按天组织的 Consumption Records 与 Items。
- **Health**：查看来自 HealthKit 的健康数据。
- **Goals**：查看和管理每日目标。

**初步设想的展示内容**：

- 当日摄入 vs 目标（蛋白质、热量等关键指标的完成度）；
- 历史趋势（体重变化、每日摄入趋势等）；
- 侧边栏 / 日历视图，按日期组织，可跳转到某一天的 Data 视图或该日期的对话上下文；
- 某条 Consumption Record 的详情，包括 Items、Group、摄入量来源、营养数据来源、是否纳入营养汇总等内部计算信息。

**编辑入口**：

- MVP 阶段 Data 面板**不提供直接编辑表单**，只提供查看、定位和"在对话中修改"入口。
- 修改历史数据时，切换到对应日期的对话上下文，通过自然语言完成。
- 后续视使用情况再评估是否增加直接编辑入口。

> Dashboard / Data 的具体信息架构、图表形式将在数据结构和记录流程明确后进一步细化，当前版本只确定 Chat 与 Data 的分层关系、按日期组织的导航方式及主要数据入口。

### 3.6 Pending Action 与轻量 Context / Modal

**Pending Action 定位**：

- PendingAction 用于保护**复杂写入操作**，主要是 Consumption Record / Item 的创建、修改、删除，以及 Nutrition DB 的写入。
- 简单写入操作（如目标修改）不走 PendingAction。

**Pending Action 交互规则**：

- Pending 由客户端**临时持久化**，App 重启后可恢复。
- 同一日期上下文中，最多一个活跃 Pending。
- Pending 绑定创建它的 Session / 日期，不跨 Session 提示、不跨 Session 阻塞。
- Pending 未解决时，**阻塞该日期上下文中的新的独立写入**，但不阻塞读操作、澄清、修正、取消。
- 用户忽略即丢弃，不落库。
- 一次输入包含多个食物时，合并为一个 Pending Record，而不是生成多个 Pending。

**Pending 时效规则**：

- Pending 有**时效（TTL）**，超时未确认则自动取消，不落库。
- 跨天自动取消：过了当天 24:00，所有未确认 Pending 自动取消。
- TTL 具体时长（是否叠加闲置超时等）见 TDD。
- Pending 取消后，不再阻塞新写入。用户如需重新记录，重新说一遍即可。

**轻量 Context / Modal 定位**：

- Agent 是统一入口，但复杂操作不应全部塞进聊天气泡。需要在对话中配合轻量 Context / Modal 完成确认、修正与数据查看。

**适用场景**：

- 上传营养成分表图片后，展示 Food Product / Food Version 的解析结果并让用户确认；
- 记录一次摄入前，展示待确认 Consumption Record Card；
- 当 Agent 需要用户澄清熟重/生重、多候选匹配（用户 Nutrition DB 或公共参考库）、用量不明确等问题时，给出轻量选择或输入界面；
- 查看某条 Record / Item 详情时，展示结构化数据而不是长文本解释。

**设计原则**：

- 聊天中保留核心结果 Card，例如"午餐 / 鸡胸肉 200g / 米饭 150g / 680 kcal / 52g Protein / 已记录"。
- Context / Modal 承担结构化确认和轻量编辑，不把 Vita 变成复杂表单工具。
- 用户仍然可以通过自然语言完成大部分操作。

### 3.7 Onboarding

**定位**：首次使用 Vita 时，一次性完成运行所需的最小初始化，不做冗长引导。

**流程**：

1. **欢迎 + 产品定位说明**
   - 一句话说明 Vita 是 AI 健康助理，不是纯饮食记账；
   - 说明数据存在本地、HealthKit 数据只读、写入需确认。

2. **HealthKit 权限申请**
   - 分别申请读取权限和写入权限；
   - 读取：身高、体重、体脂率、出生日期、生理性别、睡眠、活动能量；
   - 写入：膳食能量、蛋白质、脂肪、碳水；
   - 用户拒绝时给出清晰提示，不阻塞后续使用，但目标生成会缺少输入。

3. **读取身体数据与缺失兜底**
   - 从 HealthKit 读取身高、体重、体脂率、出生日期、生理性别；
   - 展示已获取与缺失项；
   - 缺失项按 3.4 规则处理：体重必须手动补，否则跳过目标生成；体脂率可手动输入或估算；出生日期、生理性别缺失时一次性询问；活动能量缺失时用 BMR × 轻度活动系数估算。

4. **生成初始目标**
   - Agent 基于身体数据 + 减脂增肌目标，生成蛋白质、热量等初始目标；
   - 展示目标预览，标注数据来源（HealthKit / 手动输入 / 估算）；
   - 用户一次性确认后写入。

5. **Nutrition DB 初始化**
   - 不强制录入；
   - 给出入口：可以现在添加常吃食品，也可以之后在对话中随时添加；
   - 公共营养参考库无需用户操作，内置加载即可。

6. **完成**
   - 进入主界面，Chat 和 Data 两个入口可用。

**可跳过**：

- 允许跳过 Onboarding；
- 跳过时目标为空，Dashboard 显示"未设置目标"；
- 后续用户主动触发时，Agent 再引导生成目标；
- HealthKit 权限可以之后在设置里再开。

## 4. Agent 能力边界与设计原则

- Agent 的核心职责是：**读取数据、计算/估算、给出建议**；最终是否采纳、是否写入，始终由用户通过明确操作确认。即"AI 负责计算和建议，人负责最终拍板"，这一原则贯穿记录确认、Nutrition DB 写入、目标设定等所有涉及数据写入的场景。
- Agent 应最大化利用已有数据减少用户重复输入，但不得在存在实质性歧义时擅自制造事实。
- Agent 的能力通过"工具（tools）"的形式逐步扩展，当前版本明确的工具至少包括：
  - 查询用户 Nutrition DB 计算食物营养成分；
  - 查询公共营养参考库获取通用食材的标准营养数据；
  - 创建 Consumption Record（写入，需用户确认后触发）；
  - 追加/修改/删除已有 Consumption Record 中的 Item；
  - 删除整条 Consumption Record（写入，需用户确认后触发）；
  - 读取当日/历史摄入数据；
  - 创建/更新用户 Nutrition DB 中的 Food Product；
  - 创建 Food Version；
  - 解析原始营养标签图片；
  - 读取 HealthKit 身体数据；
  - 生成初始每日目标；
  - 修改指定目标值；
  - 后续可能扩展的分析类工具（暂未设计，待 MVP 跑通后再规划）。

**Agent 写入边界**：

- 记录一次摄入，需要用户确认。
- 修改或删除已有 Record / Item，需要用户确认。
- 将食品写入用户 Nutrition DB，需要用户确认。
- 创建新的 Food Version，需要用户确认。
- 修改目标：明确指令直接执行，模糊建议经对话内确认，首次生成经一次性确认；不走 PendingAction。
- AI Estimate 可以用于本次 Consumption Item，但不能自动沉淀为用户 Nutrition DB 的正式条目。
- Agent 可以在 Pending 阶段生成计算结果，但只有确认后才写入正式数据。
- 写入/删除/修改 Apple Health 的同步操作由 Vita 内部通过 HealthKit Sync Mapping 自动维护（见 3.3），不需要用户对每次同步单独确认，但用户对 Vita 侧数据的确认动作是触发同步的前提。

## 5. 命名

- App 名称：**Vita**
- 命名理由：兼具"生命力/生活"（vita，拉丁词根）与"维他命"（vitamin 缩写联想）双重含义，贴合健康助理的定位；同时保持简洁、不将名字局限于"饮食记录"这一单一功能，为后续能力扩展留出空间。

## 6. 明确暂缓/不做的范围

- 动态/自适应目标调整（仅做初始生成 + 手动修改）
- 面向多用户的场景与权限设计
- 上架 App Store 相关的合规、审核准备
- 独立的用户 Nutrition DB 检索/模糊匹配算法（由 LLM 语义匹配替代，除非库规模显著增长）；公共营养参考库因体量较大，使用轻量的精确匹配/别名表查询，同样不构建复杂检索算法
- Google Health / Google Health API 作为 Vita 的直接健康数据源
- 更复杂的多健康数据源冲突与 Provider Resolution Policy
- 库存管理，例如"买了 4 个番茄"不在 MVP 中作为库存动作处理
- 面向用户的修改历史 / 回滚 UI（Agent 操作日志保留在技术侧，见 TDD）
- 将没有营养成分表、完全依赖 AI 估算的食品沉淀进用户 Nutrition DB
- 极少数三级数据源均无法匹配的食物（复杂菜品/无法归类的外卖菜）的估算一致性问题
- Data 面板的直接编辑表单（MVP 只做查看、定位和跳转对话）
- Apple Watch 端展示（如表盘 Complication）——列为未来可选规划方向，不在当前版本范围内，是否落地、何时启动视后续需要评估

## 7. 数据所有权与健康数据源策略

### 7.1 数据所有权

Vita 与外部健康平台的职责边界：

| 数据 | 主要拥有者 | Vita 处理方式 |
| --- | --- | --- |
| Food Product / Food Version | Vita | Vita DB |
| 公共营养参考库 | Vita（内置静态数据） | Vita DB（只读参考） |
| Consumption Record / Item | Vita | Vita DB |
| Nutrition Calculation | Vita | Vita DB / Calculation Layer |
| User Goals | Vita | Vita DB |
| Weight / Body Fat | Apple Health 等外部健康平台 | Vita 读取 |
| Sleep / Activity / Exercise | Apple Health 等外部健康平台 | Vita 读取 |
| Active Energy | Apple Health 等外部健康平台 | Vita 读取并用于分析 |
| Dietary Nutrition | Vita | Vita 保存，并同步到 Apple Health（通过 HealthKit Sync Mapping 维护一致性） |

### 7.2 当前健康数据架构

当前 MVP 采用：

```text
外部设备 / 服务
      ↓
Apple Health
      ↕
    Vita
```

其中 Vita：

- 从 Apple Health 读取健康数据；
- 将确认后的 Vita Nutrition 数据写入 Apple Health，并通过 HealthKit Sync Mapping 在修改/删除时保持同步；
- 不要求 Vita 自己成为所有健康数据的长期存储中心。

### 7.3 Google Health 的位置

Google Health / Fitbit 目前属于 Apple Health 上游生态的一部分，而不是 Vita MVP 的直接数据源。

因此当前不需要同时维护：

```text
Google Health → Vita
Apple Health  → Vita
```

两套独立读取链路。

如果未来发现 Google Health 提供了 Apple Health 无法提供、且对 Vita 核心功能有实际价值的数据，再增加独立的 Google Health Adapter，并在届时定义数据源优先级与冲突处理规则。
