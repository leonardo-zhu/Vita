# Vita — 产品需求文档 (PRD v2.0 草案)

> 状态：已评审（2026-11-04）；M1–M3 已实现并部署，1.0 数据的真机迁移待验证，M4、M5 未开始（进度见《Vita 2.0 架构设计》§16）。本文只写 2.0 相对 1.0 的变化；没提到的产品规则沿用《Vita PRD v0.6》。技术选型与实现另立 ADR 与 TDD，本文只给产品层面的要求和待决问题。

**一句话**：1.0 证明了"对话记录 + 确认卡 + 健康数据"这条路走得通；2.0 把数据和 Agent 搬到服务端，让数据只有一份、能管理，改业务不用发 App。

------------------------------------------------------------------------

## 1. 1.0 现状

1.0（即 PRD v0.6 + 身体成分模块）功能已完成：

- 对话式记录、确认卡、按日 Session、修正与删除；确认后可自动接着做下一步（`afterConfirm`）。
- 个人食品库（营养标签由模型看图读取）+ 公共营养参考库。
- Apple 健康读写、目标设定（减脂 / 增肌 / 维持，能量目标随活动每天计算）、Onboarding。
- 体脂秤连接、离线同步、体脂率校准、完整身体成分指标。
- Vita Admin：远程配置、Prompt 调试、诊断日志（只有元数据）。

1.0 的架构是**数据只存在本机**（ADR-002 / 003）。使用下来暴露的问题：

| 问题 | 例子 |
| --- | --- |
| 脏数据没法修 | 食品名存成标签上的"生巧熔岩蛋糕 · 北京象鲜科技"，用户叫它"小象的巧克力蛋糕"，以后匹配不上；只能在对话里绕着改。 |
| 改业务要发 App | 工具参数、确认门规则、上下文拼装都在客户端，改一点就要重新构建安装。 |
| 没有备份 | 手机丢了、重装、数据迁移出错，记录就没了。 |
| 调 prompt 看不到真实效果 | Admin 只有元数据，Prompt 调试用不到真实的食品库和记录。 |
| "本地优先"拿不到好处 | 记录靠对话，对话离不开云端模型；离线本来就用不了核心功能，饮食内容也本来就会发给模型。 |

## 2. 2.0 目标与边界

**目标**

1. **数据只有一份，在服务端**：记录、食品库、目标、对话、待确认卡片、身体成分都以服务端为准。
2. **能管理**：App 和 Admin 都能直接查看、修正数据。
3. **改业务不用发版**：Agent 的工具循环、确认门、上下文都在服务端执行。
4. **食品库更好用**：按用户自己的叫法匹配；营养素不只四项。

**仍然不做**（沿用 v0.6 §6）：多用户、上架 App Store、离线对话、用户可见的修改历史 / 回滚。

## 3. 架构变化（产品视角）

```text
             ┌────────── 服务端 ──────────┐
 iPhone ───▶ │ Vita API：数据、Agent、确认门 │ ───▶ Conduit ───▶ 模型
   │         │ Vita Admin：配置、诊断、数据 │
   │         └────────────┬──────────────┘
   └── Apple 健康 / 体脂秤 / 相机（只能在手机上）
```

- **服务端是唯一数据源**。客户端不保留业务数据库，只做界面、交互和设备能力。
- **Agent 在服务端跑**。客户端发出用户消息（和标签照片），服务端组装上下文、调模型、执行工具、生成确认卡，把文字、步骤和卡片流式推回客户端。确认 / 取消也是调服务端。
- **确认门不变**（ADR-004）：模型仍然只能查询和提案，写入仍须用户在卡片上确认。
- **手机上留下的**：
  - Apple 健康：读取活动、睡眠、体重等上传给服务端；把服务端确认的饮食数据写入健康，并在修改 / 删除时同步。
  - 体脂秤：蓝牙连接和离线记录同步仍在手机，称重结果上传服务端；没网时在本地排队，有网后补传，不能丢。
  - 相机 / 相册：拍标签，照片上传服务端存档并交给模型读。
- **模型密钥不再放在手机上**：由服务端调 Conduit，手机只需要登录 Vita 服务端。

### 3.1 数据所有权（替换 v0.6 §7.1）

| 数据 | 存在哪 | 说明 |
| --- | --- | --- |
| 饮食记录、食品库、目标、对话历史、待确认卡片 | 服务端 | 唯一数据源 |
| 营养标签原图 | 服务端 | 作为食品版本的来源依据 |
| 公共营养参考库 | 服务端 | 静态只读；私有来源的数据仍不公开分发（ADR-006） |
| 体脂秤称重（原始与计算结果）、校准 | 服务端 | 手机采集、排队上传 |
| 活动、睡眠、外部来源的体重 | Apple 健康 | 手机读取后上传，供目标计算与 Agent 使用 |
| 写入 Apple 健康的饮食 / 体重 Sample | Apple 健康 | 手机负责写入并维护映射 |

## 4. 功能变化

### 4.1 数据管理（推翻 v0.6 §6"Data 面板不做直接编辑"）

- **App 的 Data 页可直接编辑**：
  - 餐食：改用量、改时间、删除条目或整条记录。
  - 食品库：改名称、品牌、常用叫法、包装规格；修改营养值时存为新版本（旧版本保留，已有记录的营养快照不变）；删除食品。
- **Admin 新增数据管理页**：浏览、搜索、修改同样的数据，适合在电脑上批量整理。
- 用户手动编辑**不走确认卡**（确认门只约束模型），但和模型提案走同一套校验，并写审计日志。
- 修改后的饮食数据照常同步到 Apple 健康。

### 4.2 食品库：按用户的叫法匹配

- 新增**常用叫法**（别名，可多个）。存库时模型把用户这句话里的叫法一起带上，比如"小象巧克力蛋糕"。
- **品牌记用户认识的名字**："小象超市"，而不是"北京象鲜科技有限公司"。标签上的委托方、生产商这类工商名记到备注里，保留来源，但不用于匹配。
- **对话里能改名、加叫法**："这个以后叫小象巧克力蛋糕"会生成确认卡。
- 匹配仍由模型按语义判断，有歧义先问（ADR-015）；别名只是给模型更多线索。

### 4.3 营养素扩展

- 除能量、蛋白质、脂肪、碳水外，新增**可选**的钠、饱和脂肪、糖（标签上通常都有，按 GB 28050 钠是强制项）。
- 来源有就存，没有就留空，不由 AI 估算补齐；日合计标明哪些条目缺这一项。
- 写入 Apple 健康的对应项（如 `dietarySodium`，需要新权限）。
- 是否给钠、饱和脂肪设上限目标，见开放问题。

### 4.4 Agent

- 工具循环、上下文拼装、`afterConfirm` 接续都在服务端执行，改了随服务端部署生效。
- **对话追踪**：Admin 可以看每一轮的原话、回复、推理摘要、工具调用与结果、卡片的确认 / 取消结局，可以按配置版本和 prompt 版本筛选，用来评估 prompt 修改的效果。取代 1.0 只有元数据的诊断日志（ADR-014）。
- Prompt 调试可以直接用真实的食品库和当天记录。

### 4.5 备份（2.0 暂缓）

- 2.0 不做异地备份。以后把数据库迁到云数据库时，备份交给云服务。
- 可以导出全部数据（JSON），作为最后一道保险，也方便将来换架构。

### 4.6 登录与设备

- 单用户。手机用 Admin“设备”页签发的设备令牌连接 Vita 服务端（只显示一次，复制粘贴进 App），不再手动填 Conduit 令牌；令牌可在 Admin 里吊销，App 设置里可以断开。
- 新设备登录后直接看到全部数据，不需要迁移。

## 5. 网络与离线

| 场景 | 没网时 |
| --- | --- |
| 对话记录 | 不可用（1.0 也一样），明确提示。 |
| 查看 Data 页 | 不可用，提示没有网络（离线缓存等有需要再做）。 |
| 体脂秤称重 | 照常称，记录在手机排队，有网后上传。 |
| 写入 Apple 健康 | 等服务端数据到手机后再写。 |

## 6. 从 1.0 迁移

- 1.0 的本机数据（记录、食品库及所有版本、目标、对话、称重、校准、标签照片）**一次性导入**服务端，导入后核对条数与每日合计。
- 迁移后 Apple 健康里不应出现重复或误删：1.0 写入的旧 Sample 按手机上的映射删掉，再按服务端数据带同步标识重写一遍（数值不变）。1.0 里因为没有权限而没写进健康的称重，迁移后若已有权限会补写进去。
- 装上 2.0 之前 1.0 照常可用；2.0 不保留 1.0 模式，首次打开连上服务端后就进迁移页。迁移时先导出一份本机数据留在“文件”App 里，核对一致才删除手机上的数据，中途被打断下次接着做。

## 7. 分期（草案）

| 阶段 | 内容 |
| --- | --- |
| M0 决策 | 新 ADR（推翻 ADR-002 / 003、修订 014），2.0 TDD：服务形态、存储、鉴权、备份、Apple 健康同步归属。 |
| M1 服务端基础 | 数据模型（直接包含别名与扩展营养素）、记录 / 食品库 / 确认卡 / 目标 API，测试随领域逻辑一起迁；全量导出。 |
| M2 Agent 上服务端 | 工具循环与确认门在服务端跑，流式推给客户端；对话追踪进 Admin。 |
| M3 iOS 改为薄客户端 | 对接 API；健康、体脂秤、相机改为采集上传；1.0 数据导入。 |
| M4 数据管理 | App Data 页编辑、Admin 数据管理页。 |
| M5 食品库与营养素 | 别名与改名的对话流程、扩展营养素的显示与健康写入。 |

## 8. 暂缓 / 不做

- 多用户、账号体系、上架 App Store。
- 离线对话、设备端模型。
- 多端实时协同编辑（单用户，以服务端为准即可）。
- 网页版客户端：架构上允许，2.0 不做。
- 身体成分遗留项（内脏脂肪、用去脂体重生成目标、秤内多用户过滤）：沿用身体成分模块的开放问题，不放在 2.0 主线。

## 9. 开放问题

技术层面的讨论与建议见《[Vita 2.0 架构设计](../architecture/vita-2.0-architecture.md)》。

1. ~~**服务形态**~~：已定，单独的 Vita API 服务，不并进 Admin（ADR-020）。
2. ~~**部署在哪**~~：已定，先放 R4S，接受迁云之前没有异地备份的风险。
3. ~~**存储**~~：已定，SQLite（`node:sqlite`），技术栈见 ADR-021。
4. ~~**登录方式**~~：已定，Admin 为设备签发令牌（架构设计 §8）。
5. ~~**Apple 健康同步**~~：手机拉取服务端的变更，用 HealthKit 的同步标识覆盖旧数据（架构设计 §9）；暂不考虑换手机。
6. ~~**Data 页离线缓存**~~：暂不做，有需要再说。
7. **营养素范围与目标**：钠、饱和脂肪、糖之外还要不要更多？要不要设上限目标？
8. ~~**对话追踪**~~：照片本来就存在服务端，追踪只引用不复制；建议文字保留 90 天（架构设计 §10.3）。
9. **App 里的编辑和 Admin 里的编辑**：范围是否完全一致？有没有只在 Admin 开放的操作（如批量合并重复食品）？
