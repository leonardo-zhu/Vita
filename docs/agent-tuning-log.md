# Vita Agent 调优记录

> 记录为了让 Vita 的对话 Agent 更可靠、更快所做的设计、修复、实验与结论，按专题整理，附时间线与测试数据。
> 新的优化、实验做完就补到这里（专题里写结论，§9 时间线加一行，测试数据放 §8）。最后更新：2026-11-11。

## 1. 基线：Agent 是怎么跑的

| 项目 | 现状 | 依据 |
| --- | --- | --- |
| 运行位置 | 2.0 起在 Vita API（服务端）；1.0 在手机上 | ADR-019 |
| 模型调用 | 服务端直接发 HTTP 到 Conduit 的 `POST /v1/responses`（OpenAI Responses API 格式），Conduit 原样转发给火山方舟；别名 `vita-chat` → `doubao-seed-2.1-lite`（2026-11-11 核实；之前是 `ark-code-latest`，用户在 Conduit 后台切换，切换日期没有记录） | ADR-005、ADR-013、`api/src/agent/llm.ts` |
| 会话状态 | 无状态：`store: false`，每轮把完整上下文重发，上一轮的推理不回传 | llm-provider.md §5 |
| 写入边界 | 模型只能查询和提出变更（确认卡），用户确认后由服务端写入 | ADR-004 |
| 食品匹配 | 个人食品库整库进系统指令，由模型按语义判断；公共参考库按名称 / 别名精确查 | ADR-015 |
| 一轮的组成 | 系统指令（prompt + 个人食品库）→ 工具 → 历史（最近 20 条）→ 当前状态（system）→ 本轮消息；稳定的放前面，命中服务商前缀缓存 | §5.1 |
| 可观测 | 每轮的原话、回复、推理、工具调用与结果、轮数、token、耗时写进 `chat_traces`（保留 90 天），Admin“对话”页可看 | 架构设计 §10.3 |

**为什么没用 OpenAI 官方 SDK**：1.0 在手机上调模型，官方没有 Swift SDK，于是用 `URLSession` 写了一个薄适配层；2.0 把它原样翻译成 TypeScript（约 350 行，有测试）。在服务端换成官方 `openai` 包是可行的（指向 Conduit），能少维护流式解析，但要重新对齐 Conduit 的错误码。不是刻意的决定，留到以后改模型调用时顺手换。

**为什么不开 `store: true` / `previous_response_id`**：Conduit 本身就不支持（会去掉 `store`，带 `previous_response_id` 返回 400）；重发上下文的成本已经被前缀缓存吃掉大半（实测第二轮约 89% 命中）；而且 rewind（把消息排除出上下文）要求上下文由服务端自己拼，接火山存的链就删不掉了，标签照片也会存到服务商那边。

## 2. 确认门与“说了出卡却没出卡”

这是调优花力气最多的一个问题：模型（ark-code-latest）有时在文字里说“已生成确认卡”，却没有调用提案工具，用户看不到卡片，也什么都没保存。

| 时间 | 现象 | 处理 |
| --- | --- | --- |
| 2026-10-31（1.0 验收） | 模型模仿历史里只有文字的回复，说卡片好了但没调工具 | 系统 prompt v3：确认卡只能由提案工具生成；历史里带卡片的回复加客户端注记 |
| 2026-11-04 | 历史注记“［客户端注：……已保存］”拼在助手的话后面，模型把这句照抄进新回复，看起来像存好了（“小象鲜牛奶”事件） | 注记改为单独一条 system 消息，不拼进助手的话；回复里出现仿冒的注记就删掉；回复声称出卡但这一轮没有卡片时，在末尾写明“这次实际没有生成确认卡，没有保存任何数据” |
| 2026-11-05 | 兜底只能“说明没存上”，卡片还是出不来 | 检测到“说了出卡却没调工具”时，服务端加一条系统提醒，再给模型一轮去真的调用；仍没调才加上面的说明 |
| 2026-11-05 | 被带偏的历史会持续影响后面的对话 | Admin“对话”页可把消息排除出上下文（rewind），手机上不再显示这些消息；历史里的旧标签照片不再重发 |
| 2026-11-05 | 确认后的接续约四分之一只说“现在记……”不调工具，这句话不含“确认卡”字样，前面的检测抓不到 | 接续第一轮发 `tool_choice: required`；仍没调工具就提醒一次（实验见 §8.3） |
| 2026-11-06 | 普通消息也会“只交代怎么记就停”（“鸭血粉丝汤”事件，见 §2.1） | 回复里有“记为 / 存为 / 按……记”这类说法、又没出卡时，同样提醒一次；仍没出卡就写明没保存 |

判断依据都来自 Admin 的对话追踪：失败的那轮 `rounds=1`、没有 steps，推理里写着“需要调用 proposeFoodChange”，但只输出了文字。

### 2.1 “鸭血粉丝汤”事件与护栏的选择（2026-11-06）

**现象**：用户发“刚刚我吃了一碗鸭血粉丝汤：100 g 红薯粉、300 g 鸭血、150 g 咸水鸭、6 颗油豆腐果（大概 30 g）……又喝了一罐无糖可乐”，模型回复“这碗按「鸭血粉丝汤」记为晚餐……无糖可乐按一罐 330 ml 记。油豆腐果……估算为约 74 kcal……”，然后就结束了。追踪：1 轮、没有工具调用；推理里已经想好了每一项怎么记（食品库 ID、豆腐果估算、可乐 330 ml、餐次 dinner），只差调用 `proposeRecordChange`。

**为什么没被接住**：服务端在模型这一轮没调工具时有两道检查——回复“声称出卡”（`claimsCard`：“生成了确认卡”“请确认下面的卡片”），或者是确认后的接续轮。这次是普通消息，回复只是在**交代打算怎么记**，没提“卡片”，两道都没触发，这一轮就空着结束了。和 §8.3 接续轮的失败是同一种毛病（说了不做），只是发生在普通消息上。

**兜底的原理**（讨论时用户问到“靠什么兜底”“提醒什么时候发生”，这里记下来）：一轮对话在服务端是一个循环，模型说完、没调工具时，循环还没告诉客户端结束。这时服务端先检查文字，认出“说了没做”就往**这次请求的输入列表**里追加一条 system 提醒（“你说了要怎么记，但没调用工具……现在直接调用”），立刻再请求一次模型。提醒只在内存里，不存进聊天记录，下一轮也不会再发给模型；用户看到的是同一个气泡里，说明之后多转了十几秒、卡片出来了。只提醒一次，仍没出卡就在回复末尾写明“这次实际没有生成确认卡”。

**考虑过的几种护栏**（从粗到细）：

| 做法 | 怎么做 | 成本 | 能接住 | 接不住 / 代价 | 对 Vita |
| --- | --- | --- | --- | --- | --- |
| 1. 文字匹配 | 正则认“说了要做”的说法，命中就提醒一次 | 几十行代码；不触发时零开销，触发时多一轮（10–15 秒） | 写进规则里的说法 | 换个说法就漏；偶尔误判，只是多问一轮 | **采用**，作为最后一道网 |
| 2. 小模型当裁判（LLM-as-judge） | 回复写完后让便宜模型判断“是否承诺了却没做” | 每轮多一次调用：延迟、费用 | 懂语义，换说法也认得出 | 每条消息都要付出；裁判本身也会错 | 暂不做：大部分轮次不需要，付出不划算 |
| 3. 结束回复也做成工具（final answer as a tool） | 必须调 `reply(intent, text)` 才能收尾，`tool_choice: required` 常开 | 改造大 | 堵死“写完文字就停”；声明了要记录却没卡片可确定地打回 | 意图是模型自己填的，它可能填“在回答”、正文却写“记为晚餐”，还得看文字；文字进了 JSON 参数，逐字输出要边收边解析半截 JSON，否则要干等整段；出卡那一轮若还要再调 `reply` 就多一轮，除非同一轮并行调用（现用模型是否稳定支持未验证）；每条消息强制调工具对回复质量和 JSON 合法性的影响要重测 | 候选：数据证明常漏时再在评测里试 |
| 4. 说明放进提案工具的参数 | `proposeRecordChange` 自带“说明”字段，客户端显示在卡片上 | 中：一个字段 + 卡片界面 | 有说明就一定有卡片，说明与卡片不会分离 | 模型仍然可以只输出文字就停（不调工具这条路还开着），所以减少但不消灭“说了不做”；说明进参数同样影响逐字显示 | 候选：和 3 一起评估 |
| 5. 以状态为准 | 不管模型说什么，只看有没有生成卡片、数据有没有变，如实告诉用户 | 低 | 不会让用户误以为存上了 | 只是如实说明，卡片还是出不来 | **已有**（2026-11-04 起的“这次实际没有生成确认卡”） |

**为什么现在选 1**：

- 成本最低：不改协议、不改客户端、不影响逐字输出；平时不触发就没有开销。
- 和 5 配合是分层的：1 尽量把卡片补出来，5 保证补不出来时如实说明，所有写入仍只经确认卡（ADR-004），误判最多多一轮，不会乱存数据。
- 3 和 4 更接近根治，但都不能单独让检查变成完全确定（模型仍可能不调工具，或者自报的意图与正文不符），而改造的代价（逐字输出、收尾规则、prompt、重新评测）要先有数据证明值得。

**这次的改动**：`announcesChange`（`api/src/agent/orchestrator.ts`）认“记为 / 记成 / 记作 / 记录为 / 存为 / 存成 / 存进 / 按……记”；回复里有问号时不算（那是先问清楚再记），“今天的记录里……”“记得多吃……”这类只是提到记录的也不算。命中且这一轮没出卡时提醒一次；`guardUnbackedCardClaim` 也认这类说法，仍没出卡就写明没保存。测试用这次的原话（`agent.test.ts`）。

**什么时候重新考虑**：给追踪记上“这一轮触发了哪种提醒”（目前提醒原文不进追踪，只能从轮数推测），跑一两周看“说了不做”有多常见、提醒后补出卡的比例、以及正则漏掉的说法。如果仍然常漏，把“说了不做”的真实对话补成 `run.mjs` 用例，在评测里对比 3 / 4 与现状的出卡率、回复质量和耗时，再决定要不要改协议。

## 3. 营养标签

| 时间 | 做法 | 原因 / 结果 |
| --- | --- | --- |
| 2026-10-31 | 手机本地 Vision OCR + 规则解析 | 第一版 |
| 2026-11-02 | 解析器在品名列识别失败时，按 GB 28050 的固定顺序（能量 / 蛋白质 / 脂肪 / 碳水 / 钠）对应数值列，并标记待核对 | 圣农鸡腿块标签的小字品名列 OCR 全错，数值列是对的 |
| 2026-11-02 | 改为照片随消息以 `input_image` 发给模型直接读，删掉本地 OCR（ADR-016） | 同一张图模型约 10 秒读对；本地识别对小字、倾斜标签不可靠 |
| 2026-11-02 | 标签的处理要求从客户端附件文字移进系统 prompt（v4）：默认就是存库，直接提案，千焦按 ÷4.184 换千卡 | 附件文字里写死的“吃了多少告诉我”让对话很生硬 |
| 2026-11-04 | 一条消息最多 6 张照片（批量录入）：每张一个食品，一天只能有一张卡，用 `afterConfirm` 逐张接续；规则写在代码里随附件发，而不是写进 prompt | Admin 发布的 prompt 会整段替换内置的，规则放 prompt 里可能被覆盖 |
| 2026-11-05 | 历史里只有最近一条带照片的消息重发原图，更早的换成一句说明 | 长对话一轮输入达 3.3 万 token，旧照片还会干扰模型 |
| 2026-11-05 | 按标签存库必须带净含量（`product.package`），缺了在提案时直接拒绝，模型当轮去找或先问用户（prompt v9） | “小笼汤包”事件：先存了没有净含量的食品，用户说“吃了一袋”时换算不了，只能确认后再补一张卡 |

## 4. 多步请求：`afterConfirm` 与接续

一天同时只能有一张待确认卡片，所以“存库 + 按整袋记录”这类请求天然要两张卡。

- **2026-11-04**：提案工具加可选的 `afterConfirm`（确认后的下一步）。用户确认后，服务端用一条客户端注记（不是用户消息）再跑一轮，模型接着出下一张卡。每张卡只能接续一次。
- **2026-11-05**：出卡成功就结束这一轮，不再为说一句“请确认卡片”多请求一次（每张卡省 10–15 秒）；prompt v7 要求模型在调用提案工具前把要说的话说完。
- **2026-11-05**：接续第一轮强制调工具（`tool_choice: required`），实测从约 75% 提高到 19/20（§8.3）。
- **2026-11-05**：已存但没有包装规格的食品，用户说“一袋”时工具报 `packageUnavailable`，错误信息里直接告诉模型：这次按克数记，确认后用 `updateProduct` 补上包装。新存的标签食品已经必须带净含量，这条只是给旧数据兜底。

## 5. 上下文、缓存与速度

### 5.1 上下文与缓存

- **2026-11-02**：每轮变化的“当前状态”（日期、revision、当天记录）从系统指令挪到本轮用户消息前的一条 system 消息，系统指令只留 prompt 与个人食品库，命中火山的隐式前缀缓存（≥1024 token 才可能命中）。之后追踪里第二轮常见 85–90% 命中。
- 历史只带最近 20 条（配置 `context.maxRecentMessages`）。
- **2026-11-05**：旧标签照片不重发、被排除的消息不进上下文（见 §2、§3）。

### 5.2 速度诊断（2026-11-04）

批量录入 3 张标签每轮约 39 秒。拆开看：

- Vita 自己的开销不到 1 秒；时间几乎都在模型。
- `ark-code-latest` 每次调用约 2 万 token 输入（含照片）要 12–17 秒才出第一个字（Conduit `usage_logs` 的 `first_token_ms`）。同一上游的 `doubao-seed-2.1-lite` 处理 3.2 万 token 只要 1–2 秒。
- 每张卡要两次调用（出卡一次、卡片后说一句话又一次）。

已做：出卡即结束（§4）、旧照片不重发（§3）。没做：换模型（准确度还没对比）。

### 5.3 “每一轮都在思考”（2026-11-05）

用户观察到接续的每一轮都会重新思考。原因：请求无状态，上一轮的推理不回传，模型每轮从头读上下文再想一遍。但实测（§8.2、§8.3）：

- 真实对话里每轮推理只有几百字，占 2–3 秒；每轮 10–15 秒主要花在读约 2 万 token 的输入上。
- 关掉思考在接续轮能快约 6 秒，但**不能和“强制调工具”一起用**：关思考时上游没严格执行 `required`，出卡率反而降到 11/20。
- 结论：思考保持 `low`，靠减少调用次数和强制调工具来提速、提可靠性。

## 6. 模型参数

| 参数 | 结论 | 来源 |
| --- | --- | --- |
| `temperature`、`top_p` | 该模型直接 400，不能用 | ADR-017（2026-11-02） |
| `reasoning.effort` | 内置默认 `low`；`minimal` 能把推理降到 0 | ADR-017、§8.2 |
| `thinking: {type: disabled}`（豆包自有参数） | 能把推理降到 0，经 `extraBody` 透传 | §8.2 |
| `thinking: {type: auto}` | 上游拒绝（400） | §8.2 |
| `tool_choice: required` | 配合 `low` 思考有效；关思考时上游不严格执行 | §8.3 |
| 参数透传 | Conduit 对原生支持 Responses 的上游（火山）直接转发，只去掉 `store`、`metadata`；不认的参数由上游返回 400 | llm-gateway-project.md |

模型参数可以在 Admin 发布（`llm.reasoningEffort`、`llm.extraBody`），Prompt 调试页能在发布前试出 400。

## 7. 食品库与数据质量（M5 及之后）

- 常用叫法（aliases）进系统指令和搜索结果，给模型更多匹配线索；品牌记用户认识的名字，工商名进备注（prompt v6）。
- 对话里改名、加叫法、补包装走 `updateProduct` 确认卡。
- 钠、饱和脂肪、糖只在来源上有时存，AI 估算的一律去掉，不让模型“补齐”编出来的数。
- 按标签存库必须带净含量（§3）。
- 名称简短（2026-11-05，prompt v10）：名称用平时会说的叫法，完整品名进备注。固定用例里 ark-code-latest 10/10 起名为“摩可纳 8 号”。
- 菜品归组（2026-11-11，prompt v11）：一道菜或一杯饮品由几样食品组成时（拿铁 = 咖啡 + 牛奶），各项填同一个 `groupName`，卡片和记录详情据此把它们归在菜名下；几样各自单独吃的不填，不自己编菜名。之前 prompt 里没提 `groupName`，工具参数只写了“可选的菜品名”，模型多半不填，偶尔又把每项自己的名字填进去。不在服务端强制：是不是一道菜只有模型能从用户的话里判断，测试数据见 §8.7。
- 烹调用油（2026-11-11，prompt v12）：“红烧罗非鱼、清炒小白菜”的记录里一滴油都没算，模型还在回复里说“用油没单独计”，热量少了约两三百千卡。v12 要求炒、清炒、红烧、煎、炸、干锅的菜另加一项植物油（一道菜一般 5–15 g，红烧、干锅、炸取高，aiEstimated），和菜归同一个 `groupName`；用户说了少油 / 无油或给了用量就照用户的。参考库的大豆油补了别名“植物油 / 食用油 / 烹调油 / 炒菜油”：参考库只做精确匹配，模型查“植物油”“食用油”原来都查不到，只能自己按 9 kcal/g 估。
- 追加时改分组（2026-11-11）：补记“油”时模型只给新项分组，已记的鱼留在组外（推理里写着“红烧罗非鱼对应组名无需调整”）。把已有项挪进组原来要另出一张 `replaceItem` 卡，一天只能有一张卡，模型就省掉了。`appendItems` 加了可选的 `regroup`，一张卡同时追加和改分组；上下文里每项附上所属的菜名。
- 漏项（2026-11-11）：说了三样只记一样，见 §8.8。v12 加了一句“提案前核对每样都在卡上”。服务端不拦：它不知道用户说了几样，确认卡本身就是最后一道关。

## 8. 测试记录

测试用 Conduit 的专用 key `vita-chat-test`（存在本机钥匙串，见 `tools/agent-eval/README.md`），和正式流量分开统计。

### 8.1 方法上的一个坑（2026-11-05）

第一次对比时用文字搜索整段响应来判断“有没有调工具”，三种设置都是 20/20。后来发现 Responses API 的响应会**原样带回请求里的 `tools` 和 `instructions`**，工具名和食品 ID 不管有没有调用都会出现。改为解析 `output` 里的 `function_call` 后重跑，才得到下面的真实数字。之后的测试一律解析结构，不搜文字。

### 8.2 思考参数：简单请求（2026-11-05）

问题“一个鸡蛋大约多少千卡”，不带工具：

| 参数 | 推理 token |
| --- | --- |
| 不传 | 160 |
| `effort: low` | 38 |
| `effort: minimal` | 0 |
| `thinking: disabled` | 0 |
| `thinking: auto` | 400 |

带一个提案工具、接续场景的小 prompt，各 3 次：`minimal` 有 1 次该调没调，`low` 3 次都调了。样本太少，于是做了 §8.3。

### 8.3 确认后接续：真实规模请求，每种 20 次（2026-11-05）

请求：内置 prompt v7 + 个人食品库（摩可纳咖啡、小象鲜牛奶）+ 全套工具 + 对话历史（存牛奶 → 已确认）+ 接续注记“按 2 g 冻干咖啡 + 300 ml 鲜牛奶记录拿铁”，约 1 万字。每次 5 个并发。判断：是否调了 `proposeRecordChange`，两项的用量与 `foodVersionId` 是否都对。脚本：`tools/agent-eval/continuation.mjs`。

| 设置 | 出卡 | 用量与 ID 都对 | 平均耗时 | 平均推理 token |
| --- | --- | --- | --- | --- |
| `low`（当时线上） | 15/20 | 14 | 14.2 秒 | 145 |
| `minimal` | 14/20 | 14 | 8.2 秒 | 0 |
| `thinking: disabled` | 14/20 | 14 | 8.4 秒 | 0 |
| `low` + `tool_choice: required` | **18/20**（另 1 次先查食品库，下一轮会出卡） | 18 | 13.6 秒 | — |
| `thinking: disabled` + `required` | 11/20 | 11 | 6.5 秒 | 0 |

没出卡时模型说的是“牛奶已存好，现在记下午的拿铁：……确认后保存”这类话，不含“确认卡”字样，所以 §2 的“声称出卡”检测抓不到。

结论与上线：接续第一轮 `low` + `required`，仍没调工具就提醒一次（2026-11-05，`6d8e18d`）。

### 8.4 真实对话的耗时（2026-11-04 的追踪）

| 类型 | 轮数 | 推理字数 | 输入 token | 耗时 |
| --- | --- | --- | --- | --- |
| 用户消息 | 1–5 | 121–1172 | 6k–62k | 17–65 秒 |
| 确认后接续 | 2–4 | 232–1067 | 21k–122k | 18–105 秒 |

122k 那次是旧照片每轮重发造成的（已修）。推理字数和耗时没有明显关系，轮数和输入量才是主因。

### 8.5 固定用例与模型对比（2026-11-05）

`tools/agent-eval/run.mjs`：四个来自真实问题的用例，用真实标签照片，只看模型第一次回应（服务端兜底不参与）。prompt v10、`effort: low`，每个用例 10 次。耗时是整个响应（非流式）的时间，不是首字时间。

| 用例 | ark-code-latest（现用） | doubao-seed-2.1-pro | doubao-seed-2.1-lite |
| --- | --- | --- | --- |
| 接续：牛奶确认后记拿铁 | 9/10，13.8 秒 | 9/10，7.7 秒 | 9/10，7.7 秒 |
| 标签缺净含量：小笼汤包 | 10/10，19.8 秒 | 10/10，8.1 秒 | 9/10，10.6 秒（1 次把净含量编成 400 g） |
| 名称简短：摩可纳咖啡 | 10/10，21.1 秒 | 6/10，10.5 秒（3 次名字略长，如“摩可纳 8 号冻干咖啡”；1 次工具参数不是合法 JSON） | 9/10，8.5 秒（1 次上游 502） |
| 历史里有假出卡：重发牛奶 | 10/10，20.2 秒 | 10/10，6.7 秒 | 9/10，6.1 秒（1 次上游 502） |
| 合计 | **39/40** | 35/40 | 36/40 |

- ark-code-latest 最准，但慢一倍左右。
- pro 的失败大多是名字比阈值（10 个字）长一点，属于观感问题；另有 1 次参数 JSON 不合法（服务端会拒绝，模型下一轮重来，多花一轮时间）。
- lite 有 1 次**编造了净含量**（照片看不清，它写了 400 g，实际 288 g），这是会写错数据的失败；另有 2 次上游 502。
- 第一轮每个用例 5 次的结果方向一致：ark-code-latest 19/20、lite 18/20、pro 19/20。
- 关于“lite 首字只要 1–2 秒”（§5.2）：那是从 Conduit 日志里看到的其他使用场景，不是 Vita 的请求；在 Vita 的真实请求上，lite 和 pro 整个回复约 6–11 秒，比现用模型快一倍左右，没有快到十倍。
- 结论：要换模型优先考虑 pro。2026-11-05 决定暂时保持 ark-code-latest，之后由用户根据实际体验再定。2026-11-11 补充：用户已把 `vita-chat` 切到 lite（为了速度），见 §8.8。换的话在 Conduit 后台把 `vita-chat` 别名指向 `doubao-seed-2.1-pro`，或在 Admin 发布 `llm.modelId`，不用改代码。

另外，第一次跑 lite 时它返回的工具参数末尾多了一个 `}`，评测脚本解析失败直接崩了。现在脚本把这种情况记为失败（“工具参数不是合法 JSON”），而不是中断。

### 8.8 漏项、烹调用油与模型对比（2026-11-11）

起因：“红烧罗非鱼一斤、300g 清炒小白菜、100g 生大米”，lite 查了三样参考库，推理里写“三样分别记”，提案却只带了鱼，回复照样说小白菜和米饭“按……记”。服务端没有丢项，是模型自己只写了一项。

`run.mjs` 新增“多样漏项”（重放那次的三次查询，看卡上三样是否都在）。一开始判“第一次回应没出卡”为失败，`--dump` 打出原始响应才发现那几次都是又调了一次工具（查烹调用油、看当天记录），在线上是正常流程；改为“还在查”不算失败后，同一用例各 20 次（prompt v11）：

| 模型 | 通过 | 平均耗时 | 失败 |
| --- | --- | --- | --- |
| ark-code-latest | 19/20 | 23.1 秒 | 1 次（当时的判法） |
| doubao-seed-2.1-pro | 19/20 | 23.3 秒 | 1 次漏项：items 为空（服务端以 `emptyRecord` 拒绝，模型重来） |
| doubao-seed-2.1-lite（现用） | 19/20 | 16.0 秒 | 1 次漏项：只有“罗非鱼净肉、红烧烹饪油” |

漏项能复现，约 1/20，三个模型都有，不是 lite 独有；lite 只在 JSON 不合法（偶发）上比另两个多。换模型解决不了这类问题。

prompt v11 → v12，lite，每个用例 10 次（“已查到油”的两个变体在历史里放一次植物油查询，只看最后出的卡）：

| 用例 | v11 | v12 |
| --- | --- | --- |
| 烹调用油：清炒小白菜（去查油或带油出卡） | 1/10 | 10/10 |
| 烹调用油（已查到油） | 8/10 | 9/10 |
| 多样漏项 | 9/10 | 10/10 |
| 多样漏项（已查到油，还要带油） | 8/10 | 8/10 |
| 其余六个 | 55/60 | 56/60 |
| 合计 | 81/100 | 93/100 |

v12 下清炒小白菜估 8–10 g 油。加上 `regroup` 后新增“补项并归组：红烧鱼补油”（重放用户补记的原话，要求把已记的鱼和新的红烧用油归到同一组）：9/10，失败的一次是先去看了当天记录。

## 11. 还没做 / 可以试

- 换模型：已对比（§8.5），pro 快一倍、准确度略低；2026-11-05 决定暂时不换。
- 推理回传：Responses API 可以把上一轮加密的推理原样传回（`include: ["reasoning.encrypted_content"]`），能让接续轮接上思路，但不会省掉思考；火山与 Conduit 是否支持未验证。
- 用户消息的第一轮是否也该强制调工具：大部分消息需要查或提案，但反问澄清、闲聊、从上下文就能答的不需要，强制会逼它先白调一个工具，多一轮；没试。“结束回复做成工具”（§2.1 的 3）是让它能常开的做法。
- 追踪里记下触发了哪种提醒（声称出卡 / 交代了怎么记 / 接续没调工具）与提醒后是否出卡，作为 §2.1 是否升级护栏的依据。
- 拼盘类标签（一张标签几列、各是一种食品，如“火锅豆制品拼盘”）：按列拆成几个食品、组件不强制净含量；“每块约 N g”让按块记不靠估算。2026-11-06 讨论过，没做。
- 评测集继续扩充：新出现的问题补成 `run.mjs` 的用例。
