## 1. 背景与定位

Vita 分发后，用户不会有自己的 Ark Key，Key 必须由服务端持有；同时需要用量与成本控制、Provider 切换、统一日志。这些能力与具体业务无关，后续其他项目接入 LLM 时会重复需要。因此把它做成独立的、多应用共用的网关，而不是 Vita 的一个模块。

**一句话：** Conduit 是自托管的、多应用的 LLM 调用网关，负责鉴权、路由、配额、成本记账和调用日志，对调用方暴露 OpenAI Responses API 兼容接口。

### 1.1 目标

1. 调用方只面对一套稳定的接口和**逻辑模型名**，不关心上游是哪个 Provider。
2. 上游 Key 只存在于服务端，调用方永远拿不到。
3. 每个应用、每个用户都有独立的限流、预算和用量统计。
4. 切换模型、切换 Provider、主备降级，不需要调用方发版。
5. 默认只记录元数据，内容记录是显式开启的例外。
6. 多应用从第一天起就是数据模型的一部分，但**只实现 Vita 需要的功能**。

### 1.2 非目标

- 不做面向公众的开放平台、不做计费收款。
- 不做 Prompt 管理与业务编排（那是各应用自己的事，Vita 的在其远程配置里）。
- 不做模型训练、微调、RAG、向量库。
- 不做业务数据存储。网关不是备份服务。
- 不重新发明所有 Provider 适配：优先复用成熟库（见 §10）。

## 2. 核心概念

| 概念 | 说明 |
| --- | --- |
| **App** | 接入方应用（如 `vita`）。配额、日志、模型权限的隔离单位。 |
| **Principal** | 一次调用的主体：某个 App 下的某个终端用户或设备（匿名 ID）。 |
| **Upstream** | 一个上游 Provider 连接：类型、Base URL、加密保存的 Key、可用模型列表。 |
| **Model Alias** | 逻辑模型名，如 `vita-chat`。调用方只用别名；别名映射到一条路由策略。 |
| **Route Policy** | 别名的路由规则：主上游与模型、备用链、超时、重试、参数覆盖。 |
| **Token** | 调用方使用的访问令牌，由 Conduit 签发与管理：所属 App、有效期、额度、限流、可用别名、状态。类似 NewAPI 的令牌模型。 |
| **Usage Record** | 每次调用一条记录：谁、哪个别名、哪个上游、token、耗时、成本、状态。 |

别名是最重要的解耦点：Vita 的远程配置里 `llm.modelId` 将填别名，真正的模型 ID 在 Conduit 里改，改完立即生效。

## 3. 对外接口

### 3.1 数据面（调用方使用）

- `POST /v1/responses`：OpenAI **Responses API** 兼容的**无状态子集**，必须支持**流式（SSE）**、**function calling**、**图片输入**。请求一律按 `store: false` 处理，首期不支持 `previous_response_id`，Conduit 不保存会话；上下文由调用方每次完整提供。
- `GET /v1/models`：返回当前 App 可用的别名。
- 头部约定：
  - `Authorization: Bearer <token>`：见 §4。
  - `X-Request-Id`：调用方生成，贯穿日志，用于与客户端诊断日志关联。
  - `X-Client-Meta`：可选，如 `app=vita; version=0.3.1; config=2026-10-24.1`，只作日志维度，不参与鉴权。
- 错误：统一错误码与 `error.type`，区分“鉴权失败 / 配额耗尽 / 上游错误 / 上游超时 / 参数不合法”，客户端据此给出不同提示。
- 后续按需增加 `chat/completions`、Anthropic Messages 兼容入口，**不是首期**；对外协议选 Responses 是 Vita 的决定（见 Vita 的 Provider 集成规范）。

### 3.2 控制面（管理员使用）

Admin API 与数据面分开部署或至少分开路由与鉴权：App 管理、Upstream 管理、别名与路由、配额、用量查询、日志查询、Key 轮换。Admin UI 调用同一套 Admin API。

## 4. 鉴权与令牌

核心原则：**Conduit 不信任调用方本身，只信任自己签发和管理的令牌。** 移动端二进制在用户手里，任何打包进去的静态密钥都能被提取，因此一切权限（有效期、额度、范围）都由 Conduit 在服务端控制，调用方持有的令牌随时可以收紧或吊销。

### 4.1 令牌模型

| 字段 | 说明 |
| --- | --- |
| 名称 / 备注 | 便于识别，如 `vita-leonardo-iphone`。 |
| 所属 App | 令牌只能访问该 App 允许的别名。 |
| 有效期 | 绝对过期时间；可选“永不过期”但默认不推荐。到期后 401。 |
| 额度 | 总额度（金额或 token 数），可选日 / 月额度。耗尽后 429。 |
| 限流 | RPM / TPM。 |
| 可用别名 | 白名单。 |
| 可选限制 | 来源 IP 白名单、最大并发。 |
| 状态 | 启用 / 禁用 / 已吊销；最近使用时间与来源，便于发现异常。 |

存储：令牌明文只在创建时展示一次，库中只存哈希和前缀；日志永不记录令牌原文。

### 4.2 阶段

| 阶段 | 做法 |
| --- | --- |
| **现阶段（仅自己使用）** | 在 Admin 手动创建令牌，填入 Vita 设置页（存 Keychain）。有效期、额度、吊销都在 Conduit 控制，丢了设备直接吊销即可。 |
| **分发前** | 增加**设备注册**：App 用 App Attest 向 Conduit 换取按设备签发的令牌，套用该 App 的令牌模板（默认有效期、额度、限流）。无需登录体系，每设备独立计量。可选再接 Sign in with Apple 做跨设备额度。 |
| **接入方有后端时** | 后端持 App 级令牌，通过头部传终端用户 ID；Conduit 对每个用户单独计量。 |

通用要求：

- 静态长期密钥**不得**随客户端发布分发给他人；自用阶段的手动令牌是已知取舍，靠额度上限和吊销控制风险。
- 所有鉴权失败对调用方只返回统一的 401 / 403 类型，具体原因（过期、吊销、范围不符）只进服务端日志，由调用方在客户端提示“令牌无效，请更新”。

## 5. 路由与降级

- 别名 → 主路由 → 备用链（有序）。触发降级：超时、5xx、限流 429、连接失败；不对 4xx 参数错误降级。
- 每条路由可配置：超时、最大重试、参数覆盖（如强制 `temperature`、`max_tokens` 上限）。
- **流式降级规则：** 一旦已向调用方发出首个 token，就不再切换上游，直接把错误作为流内事件返回；只有首包之前允许切换。
- 熔断：对某上游连续失败达阈值，短时间内跳过，并在 Admin 里可见。
- 协议归一化：不同 Provider 的 tool call、finish reason、usage 字段在出口统一为 **Responses 语义**。上游原生支持 Responses（如火山方舟）时直接透传，不支持时由网关转换，转换逻辑封装在对应的 `UpstreamClient` 内。无法归一化的能力（如某 Provider 不支持图片）在路由配置里声明，请求不满足时直接返回明确错误，而不是静默丢弃。

## 6. 配额与成本

- 维度：App、Principal；窗口：分钟（RPM / TPM）、日、月。
- 限制类型：请求数、token 数、**预算金额**（依赖价格表）。
- 价格表按上游模型维护（输入 / 输出 / 缓存命中），每条 Usage Record 记录当时的成本，价格变更不追溯改历史。
- 超限行为可选：拒绝（429 并带 `Retry-After`）、降级到更便宜别名。
- 全局熔断：整体日预算触顶后，只放行白名单 App，防止异常流量烧钱。
- 流式调用的 token 以上游返回的 usage 为准；上游不返回时用本地估算并标记 `estimated`。

## 7. 日志与隐私

分层，与 Vita 的日志分类一致：

| 层 | 内容 | 默认 |
| --- | --- | --- |
| **元数据** | request id、App、Principal（匿名 ID）、别名、实际上游与模型、token、耗时、首 token 延迟、状态码、错误类型、降级路径、客户端元信息 | 开启，长期保留（可配置） |
| **内容** | 请求与响应的消息体 | **默认关闭**，按 App 开关，带保留期与脱敏，且需明确告知终端用户 |

要求：

- 转发过程中请求体不落盘，只在内存流转。
- 内容记录开启时必须与元数据分库或分表，独立保留期，支持按 Principal 删除。
- 日志里**永不记录**上游 Key、用户令牌原文。
- 每条 Usage Record 带 `dataClass` 字段，便于将来按级别授权查看。
- Vita 后续若要备份 / 收集用户数据，应由 Vita 自己的后端承担，不借 Conduit 的内容日志代替。

## 8. 管理后台

首期功能：

1. App 管理、**令牌管理**（创建、有效期、额度、限流、别名白名单、吊销、最近使用），上游 Key 轮换。
2. Upstream 管理：Key 加密保存，Admin 里只显示末四位。
3. 别名与路由编辑，保存前做校验，支持**一键试发**一条测试请求。
4. 配额与价格表。
5. 用量看板：按 App / 别名 / 上游 / 时间，成本、错误率、P95 延迟、降级次数。
6. 请求日志查询（元数据）。
7. 控制面操作审计（谁改了什么，保留 diff，进数据库）。

Admin 自身登录：强密码加 TOTP 或 Passkey，必要时限制 IP。

## 9. 架构与技术选型（建议）

**数据面与控制面分离：** 数据面追求低延迟、不缓冲流式，必须稳定；Admin 的发布和重启不应影响在途请求。

| 部分 | 建议 | 理由 |
| --- | --- | --- |
| 数据面 | TypeScript + Hono 或 Fastify，Node 运行 | 与团队技术栈统一；流式透传简单。要极致性能再评估 Go。 |
| Admin UI + Admin API | Next.js | 已决定使用。 |
| 存储 | PostgreSQL（元数据、配置、用量） | 单机起步也可用；SQLite 仅限最早期试验。 |
| 限流 / 计数 | Redis，或首期进程内加数据库兜底 | 单实例时可先不引入。 |
| 密钥 | 上游 Key 加密存储，主密钥来自环境或 KMS | 数据库泄露不等于 Key 泄露。 |
| 部署 | 国内可稳定访问 Ark 的区域，容器化，健康检查，自动重启 | 与 Ark 网络环境匹配。 |

Node 项目使用 pnpm。

## 10. 自研与复用的取舍

不要在首期手写所有 Provider 适配。三条路：

| 方案 | 说明 | 适用 |
| --- | --- | --- |
| A. 自研薄代理 | 首期仅 Ark（原生支持 Responses），转发加令牌鉴权加记账 | **首期推荐** |
| B. 内核换成 LiteLLM Proxy | 多 Provider、预算、降级现成，Conduit 保留鉴权与 Admin | 出现第二个 Provider 且降级需求复杂时 |
| C. 用 Vercel AI SDK 之类做适配库 | 只复用 Provider 适配，网关逻辑自写 | 折中 |

为了让 A→B 可平滑过渡：**内部定义 `UpstreamClient` 接口**，路由、配额、日志都依赖接口，不依赖具体适配实现。

注意：对外协议是 Responses。评估 B / C 时必须先验证其对 Responses 的流式与 function calling 支持是否完整，不满足就保持 A，或只复用其上游适配而不暴露它的入口。

## 11. 与 Vita 的对接约定

1. 客户端所有模型调用统一走 Conduit，地址写在构建配置里（Debug / Release 区分环境），不可远程改（规则见 Vita Admin 设计 §3.2 / §3.3）。
2. Vita 远程配置的 `llm.modelId` 填**别名**，如 `vita-chat`。别名到真实模型的映射由 Conduit 维护。
3. 请求带 `X-Request-Id` 与 `X-Client-Meta`（含 `configVersion`），使网关日志与 Vita 诊断日志可关联。
4. 客户端不保留直连上游的路径，也不持有上游 Key。因此 Conduit 的可用性就是 Vita Agent 的可用性，需按 §14 做监控与快速恢复；开发期使用独立的 dev 实例。
5. 错误码映射：Conduit 的统一错误类型对应到 Vita 的用户提示，不向用户暴露上游细节。
6. Vita 不再需要在客户端处理多 Provider 差异，该复杂度收口在网关。

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |

## 14. 风险

- **平台化过早：** 在只有一个接入方时，容易提前做太多通用性。对策：数据模型多租户，功能只做 Vita 用得上的。
- **单点：** 网关挂掉等于所有接入方不可用。对策：健康检查、自动重启、多实例或可快速重建、监控告警；数据库故障时数据面应能用缓存的路由配置降级运行。Vita 客户端没有直连逃生口，所以这一条是硬要求。
- **成本失控：** 对策：多层预算与全局熔断。
- **Key 泄露：** 对策：加密存储、不进日志、可快速轮换。
- **隐私合规：** 对策：默认不记内容、不落盘请求体、独立保留期、可删除。
